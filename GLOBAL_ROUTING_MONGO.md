# Global Routing & Data Residency — Architecture

> **Related documents**
> - [`GLOBAL_ROUTING_MONGO_ATLAS.md`](./GLOBAL_ROUTING_MONGO_ATLAS.md) — runbook for moving the
>   database to an Atlas Global Cluster (zone sharding)
> - [`docs/infra-architecture-multi-region.md`](./docs/infra-architecture-multi-region.md) — AWS
>   multi-region infrastructure (incl. Atlas PrivateLink, Change 10d)

> **Status (what is live vs planned)**
> - **Live:** country → location assignment at registration; location-based API routing at the
>   edge to three AWS backend regions (ap-south-1, eu-west-1, us-east-1); region-scoped workers;
>   WAF geo-block (stg/prod).
> - **Live, but not yet residency-enforcing:** the database. Every region's backend uses **one
>   MongoDB Atlas cluster in ap-south-1** (free tier). Documents already carry `location` and every
>   index leads with it, so the data is shard-ready — but until the move to an Atlas Global
>   Cluster, all data physically lives in ap-south-1.
> - **Planned:** Atlas Global Cluster with 3 zones — see the runbook.

## 1. Overview

Residency is decided by **one value per user, `location`**, assigned once at registration and then
used by every layer:

```
 Registration                 Every request / job                      Storage (planned)
 ────────────                 ───────────────────                      ─────────────────
 country_code ──► location ──► AWS region that serves it ──────────────► Atlas zone that stores it
   "DE"            "eu"         eu-west-1 (Lambda@Edge, worker)           EU zone (eu-west-1 shards)
```

| Layer | Maps | Source of truth | Copies kept in sync (tests fail on drift) |
|---|---|---|---|
| Country → location | ~237 countries → 6 locations | `COUNTRY_TO_REGION` in [`backend/app/routing.py`](backend/app/routing.py) | `frontend{,-app}/src/lib/countries.ts` (selector), `frontend{,-app}/src/lib/locationHint.ts` (registration hint) |
| Location → AWS region | 6 locations → 3 regions | `REGION_TO_LOCATIONS` in `routing.py` | `LOCATION_TO_REGION` in [`jwt-validator-lambda.js.tpl`](infra-live-edge/functions/jwt-validator-lambda.js.tpl), `uploads_location_to_region` in [`cloudfront.tf`](infra-live-edge/terraform/cloudfront.tf), Atlas zone ranges generated by [`backend/tools/atlas_zone_ranges.py`](backend/tools/atlas_zone_ranges.py) |
| Blocked countries | 7 countries, never served | `BLOCKED_COUNTRIES` in `routing.py` | `waf_blocked_country_codes` in [`waf.tf`](infra-live-edge/terraform/waf.tf) |

The drift checks are [`backend/tests/test_routing.py`](backend/tests/test_routing.py) and
[`backend/tests/test_atlas_zone_ranges.py`](backend/tests/test_atlas_zone_ranges.py).

## 2. Architecture

```
                        ┌───────────────────────────────────────────────┐
  Browser / mobile ───► │ CloudFront + WAF (geo-block: stg/prod only)   │
                        │   /api/*  → Lambda@Edge (origin-request)      │
                        │            verifies RS256 JWT, reads          │
                        │            `location`, picks the regional ALB │
                        └──────┬─────────────────┬───────────────┬──────┘
                               │                 │               │
               location in/apac/me          location eu     location us/br
                               ▼                 ▼               ▼
                    ┌────────────────┐  ┌────────────────┐  ┌────────────────┐
                    │ ap-south-1     │  │ eu-west-1      │  │ us-east-1      │
                    │ ALB → API (ECS)│  │ ALB → API (ECS)│  │ ALB → API (ECS)│
                    │ worker (ECS)   │  │ worker (ECS)   │  │ worker (ECS)   │
                    │ Redis (EC)     │  │ Redis (EC)     │  │ Redis (EC)     │
                    └───────┬────────┘  └───────┬────────┘  └───────┬────────┘
                            └──────────── one MONGODB_URI ──────────┘
                                                │
                     TODAY:   single Atlas cluster in ap-south-1 (all locations)
                     PLANNED: Atlas Global Cluster — APAC / EU / AMERICAS zones,
                              documents pinned to a zone by their `location`
```

Each region's backend is the same image with the same `MONGODB_URI`; only region-specific settings
differ (`AWS_REGION`, the uploads bucket, the ALB certificate) — plus the worker's
`WORKER_SCOPE_TO_REGION=true`, which makes it process only its region's locations. Redis (ElastiCache) is deployed per region by
`infra-live-backend` and holds only rate-limit counters and locks — never user data.

## 3. The location model

### 3.1 Country → location

The user **explicitly selects their country** at registration (web/app selector, or
`country_code` on the API). GeoIP and `Accept-Language` are not used for assignment — an explicit
declaration is auditable and is what regulators treat as the strongest signal. The WAF's IP
geolocation (stg/prod) is used only to *block*, never to assign.

| Location | Served from | Covers |
|---|---|---|
| `eu` | eu-west-1 | Europe (EU/EEA, UK, CH, Balkans, UA, TR…); all of Africa except Egypt; Caucasus & Central Asia; EU outermost regions (GP, MQ, GF, RE, YT, MF) |
| `me` | ap-south-1 | Middle East incl. Egypt |
| `in` | ap-south-1 | India |
| `apac` | ap-south-1 | Rest of South Asia (PK, BD, NP, LK…), East & Southeast Asia, Oceania |
| `us` | us-east-1 | North & Central America, Caribbean, US territories (PR, GU, VI, AS, MP) |
| `br` | us-east-1 | South America |

Rules (comments in `routing.py` carry the full reasoning):

- **Territories follow their sovereign's data-protection law**, not geography (Guadeloupe → `eu`,
  Guam → `us`).
- **Sub-Saharan Africa → `eu`** for transfer-law reasons as much as latency (NDPA, POPIA, Kenya's
  DPA are GDPR-modelled). Not a substitute for a privacy-law review per market.
- **South Asia outside India → `apac`**, not `in` — same region (ap-south-1), but non-Indian
  accounts are never labelled `in`.
- **Blocked — `BY CN CU IR KP RU SY`:** never offered in the selectors; registration/Google
  sign-up returns `403 {"detail": {"code": "country_not_supported", ...}}`. CN needs AWS's separate
  China partition; the rest are under comprehensive sanctions. In stg/prod the WAF additionally
  blocks requests *from* those countries' IPs with the same response body.
- **Unknown codes are rejected (422)** — there is no silent fallback to `DEFAULT_LOCATION` for a
  supplied code. All 249 ISO 3166-1 codes are accounted for (mapped, blocked, or one of six
  uninhabited territories), plus `XK` (Kosovo).

### 3.2 What is stored

- `users` stores both **`country_code`** (what the user picked, e.g. `"NP"`) and **`location`**
  (the group, e.g. `"apac"`).
- Every other user-owned collection stores only `location`. The JWT carries only `location`.

Keeping `country_code` makes regrouping possible later (recompute `location` from it), but see 3.3.

### 3.3 `location` is immutable

A user's location is set at registration and never changes, even if they move countries. On a
sharded cluster `location` is the leading shard-key field, so changing it moves every one of the
user's documents to another zone — a multi-collection migration with no atomic guarantee. GDPR
does not require relocation; data may stay where it was lawfully collected. Changing a country's
group in `COUNTRY_TO_REGION` therefore affects **new registrations only**; existing accounts need
an explicit migration script.

## 4. Request routing

### 4.1 Lambda@Edge (`jwt-validator-lambda.js.tpl`)

Attached to `/api/*` as an **origin-request** trigger (viewer-request cannot change the origin —
CloudFront silently ignores it). Caching is disabled for `/api/*`, so it runs on every call. It
rewrites both the origin and the `Host` header to the chosen regional ALB.

| Path class | Paths | Routing |
|---|---|---|
| Pure bypass | `/api/v1/auth/login`, `/api/v1/auth/google`, `/api/health` | Always the **bootstrap region** = `backend_regions[0]` (keep `ap-south-1` first) |
| Location-aware public | `/api/v1/auth/refresh`, `/api/v1/auth/logout` | `location` from any signature-valid token (expiry ignored) in the cookie or `Authorization: Bearer`; else bootstrap |
| Register | `/api/v1/auth/register` | Session token hint, else the `X-Client-Location` header the form sends; else bootstrap. Hint only — the backend computes the real location |
| Everything else | — | Requires a valid, unexpired access token; routed by its `location`. Missing/invalid token → **401**; location with no deployed region → **503** (no default region) |

The Lambda's `REGIONAL_ALB_FQDNS` comes from `var.backend_regions` at edge-apply time: **a region
missing from that list makes all of its users' calls 503.** Apply order when adding a region:
backend Terraform → backend deploy → edge Terraform.

### 4.2 Consequence for logs

| Request | Region whose CloudWatch logs show it |
|---|---|
| Login / Google sign-in | Always ap-south-1 (bootstrap) |
| Register | The hinted location's region |
| All authenticated calls, and that user's background jobs | The user's location's region |

## 5. Tokens

Defined in [`backend/app/auth_utils.py`](backend/app/auth_utils.py); RS256, header `kid`
(rotation: `docs/jwt-keys.md`). The edge verifies the same signature with the public key.

| Token | Claims | Lifetime (default) | Stored |
|---|---|---|---|
| Access | `sub`, `iat`, `exp`, `type: "access"`, `location` | 30 min | cookie `access_token`, also returned in the body for mobile |
| Refresh | `sub`, `iat`, `exp`, `type: "refresh"`, `jti`, `location` | 24 h | cookie `refresh_token` (path `/api/v1/auth/`); server-side as a `sessions` document `{_id: jti, user_id, location, expires_at}` |

- Clients send tokens as cookies (web) or `Authorization: Bearer` (mobile); cookie wins.
- `get_current_user` ([`deps.py`](backend/app/deps.py)) reads `location` from the verified token,
  validates it against `LOCATION_RE`, and loads the user with **`{_id: sub, location}`** — a
  tampered location simply finds no document.
- Revocation: `users.tokens_revoked_at`; any token with `iat <= tokens_revoked_at` is rejected (set
  by account deletion and admin lock).

## 6. Data model

All `_id`s are application-generated UUID strings, except where noted.

| Collection | `location`? | `_id` | Contents | Planned sharding |
|---|---|---|---|---|
| `users` | ✅ | uuid | Profile, `country_code`, `location`, preferences, `password_hash`, `tokens_revoked_at`, `is_being_deleted` | `{location, _id}` |
| `sessions` | ✅ | refresh `jti` | One per refresh token | `{location, _id}` |
| `children` | ✅ | uuid | Child profiles (soft delete), `active_jobs` | `{location, _id}` |
| `observations` | ✅ | child id | Per-child observations | `{location, _id}` |
| `ninety_day_plans` | ✅ | child id | Per-child plan | `{location, _id}` |
| `growth_areas` | ✅ | uuid | Completed growth areas per user/child/area | `{location, user_id}` |
| `jobs` | ✅ | ObjectId (app key: `job_id` uuid) | Background LLM jobs; TTL 24 h after completion | `{location, job_id}` |
| `email_index` | ✅ (as data) | email | `{user_id, location}` — global uniqueness + login lookup | **unsharded** |
| `allowed_emails` | ❌ | email (lowercased) | Registration allow-list | **unsharded** |

`email_index` plays the role of a global routing table: the only place an email is resolved to a
user and their location. It is tiny and is read once per login/registration, never on the hot path.

## 7. Flows

### 7.1 Registration (`POST /auth/register`)

No transactions — a reserve-then-insert pattern with a compensating delete:

```
1. Validate body (country_code must be a known code)       → 422 otherwise
2. allowed_emails has the email?                           → 403 "Registration is not open."
3. country blocked?                                        → 403 country_not_supported
4. location = resolve_region(country_code); user_id = uuid4
5. INSERT email_index {_id: email, user_id, location}      ← reserves the email globally
     DuplicateKey → existing user?  yes → 409
                                    no  (orphan from a failed earlier attempt)
                                        → reclaim it with a guarded update, continue
6. INSERT users {_id: user_id, location, country_code, ...}
     failure → DELETE email_index entry (compensation) → 500
7. INSERT sessions {_id: jti, ...}; set cookies; return tokens
```

Google sign-up (`POST /auth/google`) follows the same steps for new accounts and requires
`country_code` (`422 country_code_required` makes the client show a country picker). Existing
accounts ignore the supplied country and keep their stored location.

### 7.2 Login (`POST /auth/login`) — two lookups, no scatter-gather

```
email_index.find_one({_id: email})                 → {user_id, location}
users.find_one({_id: user_id, location})           → targeted: one zone only once sharded
```

Querying `users` by email directly would fan out to every zone on a sharded cluster.

### 7.3 Every other request — hot path

The location comes from the verified access token; every query includes it alongside `_id` or
`user_id` (e.g. `children.find({user_id, location})`). `email_index` is never touched.

### 7.4 Refresh / logout

Refresh looks up `sessions` by `{_id: jti, user_id, location}`, checks expiry and revocation,
inserts the new session **before** deleting the old one, and re-issues both tokens. Logout deletes
`{_id: jti, location}`.

### 7.5 Account deletion (`DELETE /user/me`)

1. Mark the user `is_being_deleted` and set `tokens_revoked_at` (blocks login and all tokens).
2. Delete the user's `sessions`, then `children`, `growth_areas`, `observations`,
   `ninety_day_plans` in parallel — each filtered by `{user_id, location}`.
3. Delete the `users` document.
4. Best-effort delete of `email_index`; a leftover entry is reclaimed as an orphan on the next
   registration with that email.

A `TODO(M10+)` in `auth.py` plans to wrap steps 1–3 in one transaction once the cluster supports
it; `email_index` must stay outside (it is unsharded, so including it would make the transaction
cross-shard).

## 8. Background processing

| Process | Scope | Notes |
|---|---|---|
| Job worker ([`worker.py`](backend/worker.py)) | With `WORKER_SCOPE_TO_REGION=true` (set by the ECS task definition): only jobs whose `location` is in `REGION_TO_LOCATIONS[AWS_REGION]`. Unset (local dev): all locations | Claim, `PendingJobCount`/`ProcessingJobCount` metrics (drive that region's autoscaling), and the 30-min deadline cleanup are all scoped. Startup log shows `locations=…` |
| Expired-session cleanup ([`main.py`](backend/app/main.py)) | All locations, hourly | `delete_many({expires_at < now})` — deliberately unscoped (a scatter-gather once sharded, acceptable hourly). A Redis lock `session_cleanup:lock` makes one API task per region do it |
| `jobs` TTL index | All locations | Single-field `completed_at` TTL (24 h, terminal jobs only). TTL indexes can't be compound, so it can't include `location`; on a sharded cluster each shard expires its own documents |

Rate limiting is Redis-backed per region (`rl_ip:*`, `rl_user:*`, `llm_rate:{user_id}`), with an
in-memory fallback. Because a user's authenticated calls always land in the same region, per-region
counters behave like global ones for them; login/Google limits all count in ap-south-1.

## 9. Zone sharding design (planned)

### 9.1 Why `location` leads every shard key and index

Zone sharding pins **contiguous shard-key ranges** to zones. With `location` first, all `"eu"`
documents form one range (`{location: "eu", <x>: MinKey}` → `{location: "eu", <x>: MaxKey}`)
assigned to the EU zone; the balancer never moves them out. With anything else first, a location's
documents would be spread across every zone and residency could not be enforced. For the same
reason every index in `init_indexes()` (except the TTL index) leads with `location`, so filtered
queries are routed to one zone.

### 9.2 Zones

| Atlas zone | AWS region of its shards | Locations |
|---|---|---|
| `APAC` | ap-south-1 | `in`, `apac`, `me` |
| `EU` | eu-west-1 | `eu` |
| `AMERICAS` | us-east-1 | `us`, `br` |

Zones match the backend regions one-to-one, so a region's API and worker read and write their
users' data on shards in the same AWS region. The ranges are generated, not hand-written:
`python backend/tools/atlas_zone_ranges.py <db>`.

### 9.3 Must change before sharding

| Item | Why | Where |
|---|---|---|
| `users (location, email)` unique → non-unique | A unique index on a sharded collection must start with the **full** shard key (`location, _id`). Email uniqueness is already enforced globally by `email_index` | `database.py` |
| `growth_areas (location, _id)` unique → non-unique | Shard key is `{location, user_id}` (so the existing unique `(location, user_id, child_id, area_id)` stays valid) | `database.py` |
| MongoDB **8.0** | The worker claims with `find_one_and_update` without the full shard key (needs 7.1+ on sharded clusters) | Atlas cluster version |
| Add `location` to worker filters on `jobs` (by `job_id`) and `children` (by `_id`) | Without it each update fans out to every zone; the job document already carries `location` | `worker.py` |
| Admin `list_users` | Aggregates `users` with no `location` filter — a cross-zone scatter that also lets an operator see every jurisdiction's data at once | `routers/admin.py` |

### 9.4 Transactions

None are used today (Atlas M0 has no transaction support). The code marks `TODO(M10+)` places
(account deletion, job enqueue's count-then-insert) to wrap in transactions after the upgrade.
Keep each transaction within one user's documents (same `location` → same zone) and never include
`email_index`.

## 10. Known gaps

Found while documenting; none affect routing, but they matter for residency and deletion duties:

- **Account deletion leaves the user's `jobs`.** They disappear only via the 24 h TTL once
  terminal; non-terminal ones wait for the worker's 30-minute deadline first.
- **No purge job for soft-deleted children.** `children` has a `(location, deleted_at)` index and
  `delete_child` documents a 30-day hard delete, but nothing performs it.
- **`jobs._id` is an ObjectId** (the app key is `job_id`), unlike every other collection.
- **Admin lock/unlock take `location` from a query parameter** without `LOCATION_RE` validation.
- **`email_index._id` is the normalised email, not lowercased**, while `allowed_emails._id` is
  lowercased.
- **Existing accounts from before the full country table** keep the `location` they got then (e.g.
  `"us"` for a then-unmapped country). Their real `country_code` is stored, so a one-off migration
  can correct them.

## 11. Security & compliance considerations

- **Always query with `location` and an id.** The JWT's location is signature-verified, and a
  document only exists under its own location, so a wrong location returns nothing (404) rather
  than another user's data.
- **No cross-zone admin queries.** Support tooling should require choosing a location before
  querying user data; an unfiltered `find({})` on a sharded collection reads every jurisdiction.
- **Backups must stay in-zone.** Once on a Global Cluster, confirm each zone's snapshot storage
  region matches its jurisdiction (EU zone → eu-west-1).
- **Audit logging** (Atlas Database Auditing) exported to an S3 bucket in the same region as each
  zone.
- **Field-level encryption is not implemented.** Atlas Client-Side Field Level Encryption (CSFLE)
  or Queryable Encryption for `email`, `full_name` and `password_hash` is an option if a regulator
  or customer requires that the database operator cannot read PII.
- **IP geo-blocking is not VPN-proof.** The WAF block plus the declared-country check are
  reasonable controls, not guarantees.
- **Legal review per market** (adequacy decisions / SCCs, privacy policy listing where each
  location's data is stored) is required before launch; the groupings above are engineering
  defaults, not legal advice.
