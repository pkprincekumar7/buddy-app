## 1. Overview

Residency is decided by **one value per user, `location`**, assigned once at registration and then
used by every layer:

```
 Registration                 Every request / job                      Storage (planned)
 ────────────                 ───────────────────                      ─────────────────
 country_code ──► location ──► AWS region that serves it ──────────────► Atlas zone that stores it
   "DE"            "eu"         eu-west-1 (Lambda@Edge, worker)           EU zone (eu-west-1 shards)
```

All of it lives in **one file, [`shared/routing.json`](shared/routing.json)** — regions (with their
Atlas zone and locations), every registrable country with its location, and the blocked list. The
grouping rules and how to change them are in [`shared/README.md`](shared/README.md).

| Consumer | Gets the data by | Uses |
|---|---|---|
| Every backend service — [`common/regions_data.py`](backend/common/regions_data.py) (read through [`common/regions.py`](backend/common/regions.py)) | Generated by `node scripts/sync-routing.mjs` | Region → locations and Atlas zone; `LOCATION_RE` / `location_from_claims` token validation; worker region scoping (`locations_for_region`) |
| Auth service — [`auth/countries_data.py`](backend/auth/countries_data.py) (read through [`auth/countries.py`](backend/auth/countries.py)) | Generated by the same script | Country → location at registration (`resolve_region`), blocked-country 403 (`is_blocked`). Only auth assigns a location |
| Web + mobile — `src/lib/countries.ts`, `src/lib/locationHint.ts` | Generated by the same script | Country selector, `X-Client-Location` registration hint |
| Edge — [`infra-live-edge/terraform/routing.tf`](infra-live-edge/terraform/routing.tf) | Reads the JSON directly at plan time | Lambda@Edge location → region map, CloudFront `/uploads/{location}/*` routing, WAF geo-block |
| Atlas — [`backend/tools/atlas_zone_ranges.py`](backend/tools/atlas_zone_ranges.py) | Via `common/regions.py` | Zone ranges for the Global Cluster, per service database |

CI runs `node scripts/sync-routing.mjs --check` and fails if any generated copy is stale; the
backend tests (`common/tests/test_regions.py`, `auth/tests/test_countries.py`) also compare the
generated tables with the JSON.

## 2. Architecture

```
                        ┌───────────────────────────────────────────────┐
  Browser / mobile ───► │ CloudFront + WAF (geo-block: stg/prod only)   │
                        │   /api/*  → Lambda@Edge (origin-request)      │
                        │            verifies RS256 JWT, reads          │
                        │            `location`, picks the regional ALB │
                        └──────┬─────────────────┬───────────────┬──────┘
                               │                 │               │
               location in/apac/me          location eu     location us/br
                               ▼                 ▼               ▼
                    ┌────────────────┐  ┌────────────────┐  ┌────────────────┐
                    │ ap-south-1     │  │ eu-west-1      │  │ us-east-1      │
                    │ ALB → services │  │ ALB → services │  │ ALB → services │
                    │ + workers (ECS)│  │ + workers (ECS)│  │ + workers (ECS)│
                    │ Valkey (EC)    │  │ Valkey (EC)    │  │ Valkey (EC)    │
                    └───────┬────────┘  └───────┬────────┘  └───────┬────────┘
                            └─── each service's own MONGODB_URI ────┘
                                                │
                     TODAY:   single Atlas cluster in ap-south-1 (all locations),
                              one database per service (auth, users, children, …)
                     PLANNED: Atlas Global Cluster — APAC / EU / AMERICAS zones,
                              documents pinned to a zone by their `location`
```

Every service (auth, users, children, onboarding, discover, grow, transform, release, shared) runs
in every region, with a worker beside each one except shared. A service has its own MongoDB
database, named after it (`MONGODB_DB_NAME`, set in
[`infra-live-backend/terraform/services.tf`](infra-live-backend/terraform/services.tf)), and its own
`MONGODB_URI` in its own Secrets Manager secret (`<app>/<env>/<service>-secrets`, set by hand, so
keeping a service's value identical across regions is a convention, not something Terraform
enforces); shared has no database. Only region-specific settings differ (`AWS_REGION`, the uploads
bucket, the ALB certificate). Outside local dev (`APP_ENV=local`), workers process only their
region's locations (section 8). Valkey (ElastiCache) is deployed per region by
`infra-live-backend` and holds rate-limit counters, locks and the authz cache (role and
lock/deletion/revocation flags per user id, docs/auth-users-split.md, 9.3) — no profile data.

## 3. The location model

### 3.1 Country → location

The user **explicitly selects their country** at registration (web/app selector, or
`country_code` on the API). GeoIP and `Accept-Language` are not used for assignment — an explicit
declaration is auditable and is what regulators treat as the strongest signal. The WAF's IP
geolocation (stg/prod) is used only to *block*, never to assign.

| Location | Served from | Covers |
|---|---|---|
| `eu` | eu-west-1 | Europe (EU/EEA, UK, CH, Balkans, UA, TR…); all of Africa except Egypt; Caucasus & Central Asia; EU outermost regions (GP, MQ, GF, RE, YT, MF) |
| `me` | ap-south-1 | Middle East incl. Egypt |
| `in` | ap-south-1 | India |
| `apac` | ap-south-1 | Rest of South Asia (PK, BD, NP, LK…), East & Southeast Asia, Oceania |
| `us` | us-east-1 | North & Central America, Caribbean, US territories (PR, GU, VI, AS, MP) |
| `br` | us-east-1 | South America |

Rules (full reasoning in [`shared/README.md`](shared/README.md)):

- **Territories follow their sovereign's data-protection law**, not geography (Guadeloupe → `eu`,
  Guam → `us`).
- **Sub-Saharan Africa → `eu`** for transfer-law reasons as much as latency (NDPA, POPIA, Kenya's
  DPA are GDPR-modelled). Not a substitute for a privacy-law review per market.
- **South Asia outside India → `apac`**, not `in` — same region (ap-south-1), but non-Indian
  accounts are never labelled `in`.
- **Blocked — `BY CN CU IR KP RU SY`:** never offered in the selectors; registration/Google
  sign-up returns `403 {"detail": {"code": "country_not_supported", ...}}`. CN needs AWS's separate
  China partition; the rest are under comprehensive sanctions. In stg/prod the WAF additionally
  blocks requests *from* those countries' IPs with the same response body.
- **Unknown codes are rejected (422)**, and there is no fallback location anywhere: a token
  without a valid `location` claim is rejected (401), and every user record carries one. All 249
  ISO 3166-1 codes are accounted for (mapped, blocked, or one of six uninhabited territories),
  plus `XK` (Kosovo).

### 3.2 What is stored

- `auth.auth` (the account) stores both **`country_code`** (what the user picked, e.g. `"NP"`)
  and **`location`** (the group, e.g. `"apac"`).
- Every other user-owned collection stores only `location`. The JWT carries only `location`.

Keeping `country_code` makes regrouping possible later (recompute `location` from it), but see 3.3.

### 3.3 `location` is immutable

A user's location is set at registration and never changes, even if they move countries. On a
sharded cluster `location` is the leading shard-key field, so changing it moves every one of the
user's documents to another zone — a multi-collection migration with no atomic guarantee. GDPR
does not require relocation; data may stay where it was lawfully collected. Changing a country's
group in `shared/routing.json` therefore affects **new registrations only**; existing accounts need
an explicit migration script.

## 4. Request routing

### 4.1 Lambda@Edge ([`infra-live-edge/functions/jwt-validator-lambda.js.tpl`](infra-live-edge/functions/jwt-validator-lambda.js.tpl))

Attached to `/api/*` as an **origin-request** trigger (viewer-request cannot change the origin —
CloudFront silently ignores it). Caching is disabled for `/api/*`, so it runs on every call. It
rewrites both the origin and the `Host` header to the chosen regional ALB.

| Path class | Paths | Routing |
|---|---|---|
| Pure bypass | `/api/v1/auth/login`, `/api/v1/auth/google`, `/api/health` | Always the **bootstrap region** = `backend_regions[0]` (keep `ap-south-1` first) |
| Location-aware public | `/api/v1/auth/refresh`, `/api/v1/auth/logout` | `location` from any signature-valid token (expiry ignored) in the cookie or `Authorization: Bearer`; else bootstrap |
| Register | `/api/v1/auth/register` | Session token hint, else the `X-Client-Location` header the form sends; else bootstrap. Hint only — the backend computes the real location |
| Everything else | — | Requires a valid, unexpired access token; routed by its `location`. Missing/invalid token → **401**; location with no deployed region → **503** (no default region) |

The Lambda's `REGIONAL_ALB_FQDNS` comes from `var.backend_regions` at edge-apply time: **a region
missing from that list makes all of its users' calls 503.** Apply order when adding a region:
backend Terraform → backend deploy → edge Terraform.

### 4.2 Consequence for logs

| Request | Region whose CloudWatch logs show it |
|---|---|
| Login / Google sign-in | Always ap-south-1 (bootstrap) |
| Register | The hinted location's region |
| All authenticated calls, and that user's background jobs | The user's location's region |

## 5. Tokens

Issued only by the auth service, in [`backend/auth/app/tokens.py`](backend/auth/app/tokens.py)
(lifetimes from `JWT_ACCESS_EXPIRE_MINUTES` / `JWT_REFRESH_EXPIRE_HOURS` in
[`auth/app/runtime.py`](backend/auth/app/runtime.py)); RS256, header `kid` (rotation:
`docs/jwt-keys.md`). Every service verifies them with `JWT_PUBLIC_KEYS`
([`backend/common/authz.py`](backend/common/authz.py)), and the edge verifies the same signature.
Claims in full: docs/auth-users-split.md, 9.2.

| Token | Claims | Lifetime (default) | Stored |
|---|---|---|---|
| Access | `sub`, `location`, `iss`, `aud`, `iat`, `iat_ms`, `exp`, `type: "access"`, `role` | 30 min | cookie `access_token`, also returned in the body for mobile |
| Refresh | `sub`, `location`, `iss`, `aud`, `iat`, `iat_ms`, `exp`, `type: "refresh"`, `jti`, `family_id` | 24 h | cookie `refresh_token` (path `/api/v1/auth/`); server-side as an `auth.sessions` document `{_id: jti, user_id, location, family_id, expires_at, …}` |

- Clients send tokens as cookies (web) or `Authorization: Bearer` (mobile); cookie wins
  (`extract_token`).
- `Authorizer.authenticate` (`common/authz.py`) reads `location` from the verified token
  (`location_from_claims` in `common/regions.py`, validated against `LOCATION_RE`) — a missing or
  malformed one is a **401**, never a default. Services then query with `{…, location}`, so a
  wrong location simply finds no document.
- Revocation, lock and deletion are checked on every request against the per-region authz cache
  (`authz:{sub}`, filled from auth on a miss): `deleting` → 401, `locked` → 403,
  `revoked_at_ms >= iat_ms` → 401; no entry and no answer from auth → 503
  (docs/auth-users-split.md, 9.3). `auth.auth.tokens_revoked_at` is set by account deletion,
  admin lock and role change, log-out-everywhere and refresh-token reuse.

## 6. Data model

Each service owns one database, named after it; no service reads another's database (services
copy what they need from events, docs/auth-users-split.md, 7). All `_id`s are
application-generated UUID strings, or a child id for per-child documents (`{child_id}:{area_id}`
for growth areas). The authoritative list of each database's collections, and which are sharded,
is `SHARDED` / `UNSHARDED` in
[`backend/tools/atlas_zone_ranges.py`](backend/tools/atlas_zone_ranges.py); the indexes are in each
service's `app/store.py` (plus `common/models.py`, `common/events/store.py`,
`common/upload_tracking.py`) and are listed in docs/auth-users-split.md, 14.

| Database | Zone-sharded on `{location, _id}` (planned) | Unsharded |
|---|---|---|
| `auth` | `auth` (credentials, role, `country_code`, `location`, `is_locked`, `is_being_deleted`, `tokens_revoked_at`), `sessions` (one per refresh token), `audit` | `email_index`, `allowed_emails`, `deletions`, `admin_count`, `worker_state` |
| `users` | `users` (profile) | — |
| `children` | `children` (soft delete), `pending_uploads` | — |
| `onboarding` | `conversations`, `child_access` | — |
| `discover` | `personalities`, `child_access`, `onboarding_inputs`, `jobs` | — |
| `grow` | `growth_areas`, `child_access`, `onboarding_inputs`, `personality_inputs`, `jobs` | — |
| `transform` | `plans`, `child_access`, `onboarding_inputs`, `personality_inputs`, `growth_inputs`, `jobs`, `pending_uploads` | — |
| `release` | `observations`, `child_access`, `onboarding_inputs`, `growth_inputs`, `jobs` | — |

Every database above also has `outbox`, `tombstones` and `guards` (common/events), zone-sharded
like the data they are written with. `child_access` and the `*_inputs` collections are a service's
local copies of other services' data. The shared service has no database.

`email_index` plays the role of a global routing table: the only place an email (as its HMAC key,
docs/auth-users-split.md, 6) is resolved to a user and their location. It is tiny and is read once
per login/registration, never on the hot path.

## 7. Flows

### 7.1 Registration (`POST /api/v1/auth/register`)

In [`auth/app/registration.py`](backend/auth/app/registration.py) — a saga, not one
transaction, because `email_index` is unsharded and `auth.auth` is sharded
(docs/auth-users-split.md, 10.1):

```
1. Validate body (country_code must be a known code)       → 422 otherwise
2. allowed_emails has the email's key?                     → 403 otherwise
3. country blocked?                                        → 403 country_not_supported
4. location = resolve_region(country_code); user_id = uuid4
5. Reserve: email_index {_id: <HMAC key>, status: reserved, user_id, location}
     (a stale reservation, older than 15 min, is taken over)
6. INSERT auth.auth {_id: user_id, location, country_code, ...}
7. Profile: users' PUT /internal/users/{id}
8. Activate the reservation; create the session; set cookies; return tokens
```

Each failure undoes the steps before it; what an undo can't finish is left to auth's worker
(the reaper). Google sign-up (`POST /api/v1/auth/google`) follows the same steps for new
accounts and requires `country_code` (`422 country_code_required` makes the client show a
country picker). Existing accounts ignore the supplied country and keep their stored location.

### 7.2 Login (`POST /api/v1/auth/login`) — two lookups, no scatter-gather

```
email_index.find_one({_id: <HMAC key>})            → {user_id, location}
auth.find_one({_id: user_id, location})            → targeted: one zone only once sharded
```

Querying `auth.auth` by email directly would fan out to every zone on a sharded cluster.

### 7.3 Every other request — hot path

The location comes from the verified access token; every query includes it alongside `_id` or
`user_id` (e.g. `children.find({user_id, location})`). `email_index` is never touched.

### 7.4 Refresh / logout

Refresh rotates the session within its `family_id`, with reuse detection
(docs/auth-users-split.md, 9.1). Logout deletes the session; `POST /api/v1/auth/logout-all`
deletes all of them and sets `tokens_revoked_at`. Expired sessions are removed by a TTL index on
`sessions.expires_at` ([`auth/app/store.py`](backend/auth/app/store.py)); there is no cleanup task.

### 7.5 Account deletion (`DELETE /api/v1/auth/account`)

In [`auth/app/deletion.py`](backend/auth/app/deletion.py) (docs/auth-users-split.md, 10.3):

1. One transaction in the user's zone: `is_being_deleted`, `tokens_revoked_at`, every session
   deleted, and the `user.deletion_requested` event in the outbox.
2. Outside it (unsharded): the `deletions` row listing the services expected to confirm; the
   authz cache entry becomes `deleting`, so every service refuses the user at once.
3. Each service deletes its own data for `{user_id, location}` and publishes `user.data_deleted`.
4. When all have confirmed, auth's worker deletes `email_index`, then `auth.auth`, then the
   `deletions` row — the credentials go last, so a stuck deletion can still be resumed.

## 8. Background processing

Each service except shared has a worker (`python -m <svc>.worker`): its outbox relay, its event
consumer, and its own background jobs. Region scoping comes from `locations_for_region(AWS_REGION)`
in [`common/regions.py`](backend/common/regions.py); with `APP_ENV=local` a worker handles every
location, and an `AWS_REGION` missing from `shared/routing.json` fails at startup.

| Process | Scope | Notes |
|---|---|---|
| Outbox relay ([`common/events/relay.py`](backend/common/events/relay.py)) | Rows whose `region` is the task's own `AWS_REGION` | So a shared database doesn't publish each event once per region |
| Generation jobs — discover, grow, transform, release ([`common/generation/jobs.py`](backend/common/generation/jobs.py)) | Jobs whose `location` is in this region's locations | Claim, `PendingJobCount` and the other job metrics (drive that region's worker autoscaling) are scoped; a claim older than 10 min is taken over |
| Children's 30-day purge of soft-deleted children ([`children/worker.py`](backend/children/worker.py)) | This region's locations | Hourly |
| Auth's stuck-deletion check, reaper and authz stream ([`auth/worker.py`](backend/auth/worker.py)) | Stuck check: this region's locations | Logs `auth.deletion.stuck` for a deletion older than 24 h |
| TTL indexes | All locations | `sessions.expires_at`, `jobs.completed_at` (7 days), outbox/tombstones/guards/audit. TTL indexes can't be compound, so they can't include `location`; on a sharded cluster each shard expires its own documents |

Rate limiting is Valkey-backed per region ([`common/limiter.py`](backend/common/limiter.py),
[`common/generation/llm_limit.py`](backend/common/generation/llm_limit.py)), with an in-memory
fallback. Because a user's authenticated calls always land in the same region, per-region
counters behave like global ones for them; login/Google limits all count in ap-south-1.

## 9. Zone sharding design (planned)

### 9.1 Why `location` leads every shard key and index

Zone sharding pins **contiguous shard-key ranges** to zones. With `location` first, all `"eu"`
documents form one range (`{location: "eu", <x>: MinKey}` → `{location: "eu", <x>: MaxKey}`)
assigned to the EU zone; the balancer never moves them out. With anything else first, a location's
documents would be spread across every zone and residency could not be enforced. For the same
reason every index on a to-be-sharded collection leads with `location`, so filtered queries are
routed to one zone. The exceptions are deliberate: single-field TTL indexes (TTL indexes can't
be compound), indexes on the unsharded collections (`email_index`'s `{user_id}`, for example), and
a few region-wide sweeps that don't filter by user — the outbox relay's `{region, published_at,
created_at}`, children's partial `{deleted_at}` (the purge) and `pending_uploads.created_at`.

### 9.2 Zones

| Atlas zone | AWS region of its shards | Locations |
|---|---|---|
| `APAC` | ap-south-1 | `in`, `apac`, `me` |
| `EU` | eu-west-1 | `eu` |
| `AMERICAS` | us-east-1 | `us`, `br` |

Zones match the backend regions one-to-one, so a region's services and workers read and write
their users' data on shards in the same AWS region. The ranges are generated, not hand-written:
`python backend/tools/atlas_zone_ranges.py [service ...]` prints them for each named service's
database (every database when none is named).

### 9.3 Must change before sharding

| Item | Why | Where |
|---|---|---|
| MongoDB **8.0** | Job workers claim with `find_one_and_update` filtered by `location` and status, not the full shard key (needs 7.1+ on sharded clusters) | Atlas cluster version |

The indexes are already shard-ready: every unique index on a to-be-sharded collection is
`{location, _id}`, and "one per child" is enforced through `_id` (docs/auth-users-split.md, 14).

### 9.4 Transactions

Used today, within one service's database: for example account-deletion start, logout-all,
job creation and each service's deletion handler run in `with_transaction`. Each transaction stays
within one user's documents (same `location` → same zone) and never includes an unsharded
collection such as `email_index` (it lives on the primary shard, so including it would make the
transaction cross-shard).

## 10. Known gaps

Found while documenting; none affect routing, but they matter for residency:

- **Admin account listing scatters.** `GET /api/v1/auth/accounts`
  ([`auth/app/admin.py`](backend/auth/app/admin.py)) reads `auth.auth` with no `location` filter;
  once sharded, mongos merges every zone's results, so an operator sees every jurisdiction's
  accounts at once.
- **Existing accounts from before the full country table** keep the `location` they got then (e.g.
  `"us"` for a then-unmapped country). Their real `country_code` is stored, so a one-off migration
  can correct them.

## 11. Security & compliance considerations

- **Always query with `location` and an id.** The JWT's location is signature-verified, and a
  document only exists under its own location, so a wrong location returns nothing (404) rather
  than another user's data.
- **No cross-zone admin queries.** Support tooling should require choosing a location before
  querying user data; an unfiltered `find({})` on a sharded collection reads every jurisdiction.
- **Backups must stay in-zone.** Once on a Global Cluster, confirm each zone's snapshot storage
  region matches its jurisdiction (EU zone → eu-west-1).
- **Audit logging** (Atlas Database Auditing) exported to an S3 bucket in the same region as each
  zone.
- **Field-level encryption is not implemented.** Atlas Client-Side Field Level Encryption (CSFLE)
  or Queryable Encryption for `auth.auth`'s `email` and `password_hash` and the profile names in
  `users.users` is an option if a regulator or customer requires that the database operator
  cannot read PII.
- **IP geo-blocking is not VPN-proof.** The WAF block plus the declared-country check are
  reasonable controls, not guarantees.
- **Legal review per market** (adequacy decisions / SCCs, privacy policy listing where each
  location's data is stored) is required before launch; the groupings above are engineering
  defaults, not legal advice.
